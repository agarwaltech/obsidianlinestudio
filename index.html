Four repositories that deliberately form one system rather than four unrelated demos. The pipeline builds a service, the QA suite verifies it, Terraform runs it on Kubernetes, and the triage bot explains the pipeline when it breaks.

Builds — the delivery path

End-to-End CI/CD Pipeline for a Containerized Service

  • Five-stage GitHub Actions pipeline: lint, a test matrix across two Python versions, multi-stage Docker build, Trivy vulnerability scan, then publish and deploy.
  • Cut final image size roughly 60% with multi-stage builds and a non-root runtime user; gated merges on a coverage threshold.
  • Smoke-tests the built image as a running container before it is ever pushed — unit tests say nothing about whether an image actually starts.
  • Deployment records the running image first, so a failed health check rolls back to the last working version automatically.

Verifies — the quality gate

Automated QA & Regression Suite

  • Four test layers, each answering a different question — smoke asks whether the build is alive, unit checks validation in isolation, sanity covers what changed, regression walks the whole contract.
  • Positive, negative, boundary and injection cases built from a shared data factory, parameterised so adding a case is one line.
  • Selenium drives a real browser using explicit waits only, never fixed sleeps — the single biggest cause of flaky UI suites.
  • A Postman collection runs through Newman in CI, and one quality-gate job blocks the merge if any layer fails.

Runs — the environment

Terraform + Kubernetes with Prometheus & Grafana

  • Modular Terraform provisions a VPC with worker nodes on private subnets, an EKS cluster, and an ECR registry with immutable tags.
  • Remote state in S3 with a DynamoDB lock, so two applies can never corrupt state.
  • Workload runs with three distinct probe types, a horizontal autoscaler with asymmetric scaling windows, and a disruption budget protecting capacity during node drains.
  • Six alert rules and a seven-panel Grafana dashboard cover what happens after deployment.

Diagnoses — where AI meets DevOps

AI-Powered CI/CD Failure Triage Bot

  • Reads a failed build log, works out why, and posts a plain-English explanation with a concrete fix as a pull-request comment.
  • A deterministic parser strips runner noise and finds the error signature first, so the model reasons over ~25 relevant lines instead of 40,000.
  • Cannot break the build it exists to explain: model calls retry with backoff, degrade to rule-based output, and the action always exits zero.
  • Packaged as a reusable GitHub composite action with configurable model, severity thresholds and Slack notifications.
